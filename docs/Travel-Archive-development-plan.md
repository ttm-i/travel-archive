# Travel Archive 開発計画

## 1. 進め方

- Fashion Archiveとは別の `travel-archive` プロジェクトとして開発する。
- 各フェーズは、実装、PC上の自動確認、iPhone確認手順の提示、利用者確認の順に進める。
- 利用者から確認結果を受け取るまで、次フェーズの大きな実装へ進まない。
- 不具合修正と軽微な表示調整は、そのフェーズ内で完了させる。
- ユーザーデータを扱う実装は、マイグレーションとバックアップ互換性を常に考慮する。

### 追加フェーズ5A: 地図絞り込みと旅行検索

この追加フェーズは閲覧機能の拡張として、フェーズ5の後に実施する。登録データの構造は変更せず、IndexedDB内の既存の旅行・訪問記録・スポット・カテゴリ関連から検索結果を組み立てる。

実装内容:

- 地図タブの絞り込みシート
- 「すべて」「今年」「過去1年」「期間指定」の期間条件
- 旅行登録と共通のカレンダーUIによる任意期間指定
- 同行カテゴリの複数選択（選択項目間はOR）
- 期間と同行カテゴリのAND結合
- 条件内旅行だけを反映した都道府県着色、ピン、クラスタ、訪問回数、旅行選択肢
- 地図上の適用条件チップ、件数、解除、0件表示
- 旅行タブのスポット名称検索
- スポットカテゴリの複数選択と「未分類」条件
- 同一スポットに対する名称・カテゴリのAND判定
- 一致したスポット数・名称を旅行カードへ表示
- 地図と旅行タブそれぞれの一時的な検索状態およびスクロール位置の保持
- 詳細画面では絞り込みを引き継がず、記録全体を表示

実装順:

1. 削除済みデータを除外して旅行・訪問記録・スポット・カテゴリを結合する純粋な検索関数を作る。
2. 期間の重複判定、同行カテゴリOR、条件間ANDの自動テストを追加する。
3. スポット名称の正規化、カテゴリOR、同一スポットANDの自動テストを追加する。
4. App上位へ地図条件と旅行検索条件を置き、タブ移動や詳細往復で保持する。
5. 地図の絞り込みシートと結果表示を実装する。
6. 旅行一覧の検索欄、カテゴリシート、一致理由表示を実装する。
7. iPhone縦画面、オフライン、大量記録で操作と速度を確認する。

自動確認:

- 旅行期間が指定期間の先頭または末尾に1日だけ重なる場合も対象になること
- 同行カテゴリを複数選択した場合、いずれかを含む旅行が対象になること
- 期間と同行カテゴリを併用した場合、両条件を満たす旅行だけが対象になること

- 全角・半角、英字の大文字・小文字、前後空白を正規化して名称検索できること
- 名称とカテゴリを別々のスポットが満たす旅行は除外されること
- 「未分類」を検索できること
- 削除済み旅行・訪問記録・スポットが結果へ混入しないこと

## 3. 開発上の優先順位

1. データを失わないこと
2. iPhoneで迷わず操作できること
3. 完全オフラインで動作すること
4. 同一スポットと複数旅行の関係が崩れないこと
5. 写真と地図が快適に表示されること
6. 見た目の演出

## 4. 想定リスクと対策

| リスク | 対策 |
| --- | --- |
| iPhoneの保存容量不足 | 画像圧縮、サムネイル、使用量表示、保存失敗時の案内 |
| 大容量ZIPで処理が停止 | 進捗表示、事前見積り、メモリ使用を抑えたZIP処理、実機試験 |
| 地図境界データが重い | 表示用と判定用を分離し、必要精度まで軽量化 |
| 県境・離島で誤判定 | 自動結果と採用結果を分離し、手動指定を提供 |
| PWA更新で表示が不整合 | 利用者操作による更新、キャッシュ世代管理、更新後テスト |
| DB変更で旧データが読めない | Dexieマイグレーションと旧DBを使った回帰テスト |
| スポット重複 | 同一県内検索、近隣候補、利用者確認。自動統合はしない |
| 誤削除 | ゴミ箱、関連件数表示、完全削除確認、バックアップ案内 |

## 5. 初回着手時の作業

次の開発ターンではフェーズ0だけに着手する。

1. `travel-archive` を独立したViteプロジェクトとして初期化する。
2. Fashion Archiveのソースを直接流用せず、PWA更新、IndexedDB、バックアップの設計パターンだけを参考にする。
3. 仮データを使った主要画面と座標入力モックを作る。
4. PC上で表示と画面遷移を確認する。
5. iPhoneで開ける確認版を用意する。
6. 利用者へフェーズ0の確認手順を提示して停止する。
